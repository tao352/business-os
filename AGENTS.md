> **AUDIENCE:** Google Antigravity, OpenAI Codex, and any AI coding agent operating on this repository.  
> **MISSION:** Build, extend, and maintain the AI-Configurable Business Operating System (Real Estate First).  
> **CARDINAL RULE:** The human owner is NOT expected to write or debug code manually. The AI agent executes with absolute engineering discipline, and the human owner decides all strategic and architectural questions.

---

## 1. The Core Principle: "AI Executes, Human Decides"

You are acting as the lead software engineer. You must never make major technical decisions silently, introduce unauthorized architectural pivots, or create unmaintainable code sprawl.

For every significant task, **BEFORE** implementing code, produce a concise **Change Plan**:

- **Goal:** What problem are we solving?
- **Proposed Change:** What architectural solution is proposed?
- **Systems Affected:** Which services or subsystems are touched?
- **Files Affected:** Specific file paths to create, modify, or delete.
- **Database Impact:** Does this require an Expand-Migrate-Contract schema migration?
- **Tenant Security Impact:** Does this affect multi-tenant isolation or RLS policies?
- **Risks & Edge Cases:** What could break under scale or network partition?
- **Test Plan:** How will this change be verified automatically?
- **Rollback Plan:** How do we safely revert if an issue occurs in production?

## 2. The 7-Step Development Protocol

Before changing code, read `docs/PROJECT_MAP.md` for the current domain map, Sources of Truth, known transitional debt, and the next architecture checkpoint. If it conflicts with executable code or a newer migration, verify the code and update the map in the same PR.

Every session and feature implementation must strictly adhere to this sequence:

```
1. READ        ──> Inspect existing documentation, tests, and domain models.
2. UNDERSTAND  ──> Trace call graphs and dependencies; verify invariants.
3. PLAN        ──> Create a concise Change Plan; flag breaking changes.
4. REVIEW      ──> Stop for human approval on high-risk/architectural tasks.
5. IMPLEMENT   ──> Write clean, typed, modular code with small file footprints.
6. TEST        ──> Run Vitest suites and multi-tenant RLS leak verifications.
7. VERIFY      ──> Manually or programmatically confirm end-to-end flow.
8. DOCUMENT    ──> Update /docs/*.md and record any Architectural Decision (ADR).
```

## 3. Absolute Architectural Invariants

### 3.1 Tenant Isolation Invariant (ZERO LEAK TOLERANCE)

- **Rule:** _Organization A must NEVER, under any circumstance, access, mutate, or infer data belonging to Organization B._
- **Implementation:**
  - Every tenant-aware database query MUST execute within a tenant-scoped session:
    ```typescript
    await withTenantContext(organizationId, async (tx) => {
      // All queries inside this block automatically enforce RLS
    });
    ```
  - Never accept `organization_id` or `tenant_id` from client-side POST bodies or query parameters. Always resolve the tenant ID from the cryptographically verified JWT session.
  - Run `pnpm test` and verify that `tests/tenant-isolation.test.ts` passes 100% of the time.

### 3.2 Controlled Customization Invariant

- **Rule:** _Customer customization MUST NEVER execute dynamic DDL (`ALTER TABLE`) or execute un-sandboxed customer code._
- **Implementation:**
  - Custom fields live in the `custom_data` JSONB column of core tables (`leads`, `units`, etc.).
  - Field definitions, labels, validation rules, and options live in `custom_field_definitions`.
  - Dynamic values are validated server-side using dynamically compiled Zod schemas before being saved.

### 3.3 Smart Rules Automation Invariant

- **Rule:** _Do not build or expose a node-and-wire visual workflow builder (like n8n) to customers._
- **Implementation:**
  - Automations follow the strict **Trigger-Condition-Action (TCA)** model.
  - All rules execute asynchronously via BullMQ on Redis.
  - Every rule execution is recorded in `audit_logs`.
  - Cascading loop prevention: rules generated by system actions are barred from triggering further rules beyond depth 3.

### 3.4 Frontend Design Standard (Taste-Skill / Anti-Slop UI)

- **Rule:** _Reject all generic AI slop UI clichés._
- **Implementation:**
  - NO centered heroes over dark mesh backgrounds with purple/cyan glowing blobs.
  - NO three equal feature cards or generic frosted glassmorphism on every container.
  - High-contrast, intentional typography: Geist, Outfit, or Cabinet Grotesk.
  - Max 1 primary accent color with saturation < 80%. Strict color temperature consistency (never mix warm and cool grays).
  - Use `min-h-[100dvh]` (never `h-screen`). Ensure viewport integrity on mobile and desktop.
  - Full tactile interactivity: button click states (`active:scale-[0.98]`), accessible ARIA states, loading skeletons, and clear error boundaries.

## 4. Code Quality & Modularity Standards

- **Small, Single-Responsibility Files:** Prefer files under 250 lines of code. Split complex logic into domain services.
- **Strict TypeScript:** `noUncheckedIndexedAccess: true` and `strict: true` are enabled. Never use `any`. Use `unknown` with Zod parsing or explicit type guards.
- **Zero Monster Monoliths:** Keep business logic in `packages/core`, types in `packages/types`, and database models in `packages/database`.
- **Structured Logging Only:** Never use `console.log` in production code. Always use `logger.info`, `logger.warn`, or `logger.error` from `@business-os/logger`, passing `correlationId` and `tenantId`.

## 5. Definition of Done (DoD)

A task or feature is **DONE** only when:

1. [ ] Code is written, strongly typed, and formatted with Prettier.
2. [ ] Vitest unit and integration tests pass cleanly (`pnpm test`).
3. [ ] Multi-tenant isolation verification test passes.
4. [ ] Relevant documentation in `/docs` is updated.
5. [ ] Any new architectural decision is documented in `/docs/DECISIONS.md`.
6. [ ] A human-readable walkthrough of the change is presented to the human owner.
